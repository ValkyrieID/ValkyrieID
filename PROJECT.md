# ValkyrieID

A minimal, lightweight OpenID Connect / OAuth 2.0 identity server built on .NET 10 (ASP.NET Core).

- **License:** MIT
- **Tenancy:** single tenant
- **Protocol layer:** implemented from scratch (no OpenIddict / Duende)
- **GitHub organization:** [github.com/ValkyrieID](https://github.com/ValkyrieID), repository `valkyrieid` (server, admin UI, tests, docs)
- **Documentation:** https://valkyrieid.liesel.dev

## 1. Goals

- Small footprint: small Docker image, low memory, minimal dependencies.
- Spec-compliant OpenID Provider, targeting the OpenID Foundation conformance suite (Basic OP profile).
- Runs as a single instance by default; can scale horizontally when Redis is configured.
- Simple to operate: first-run setup wizard, admin UI, sensible defaults.

## 2. Non-goals

- SQL Server support
- Multi-tenancy / realms
- Token exchange (RFC 8693)
- Implicit flow, resource owner password grant
- Consent screens
- Dynamic client registration
- Front-channel logout
- OpenID Connect Session Management 1.0 (`check_session_iframe`)
- Official OpenID Certification (requires a paid OpenID Foundation membership). ValkyrieID runs and publishes the free conformance suite results instead (§13); may be revisited later.

## 3. Storage

- EF Core with two providers: **SQLite** and **PostgreSQL**, with migrations maintained for each.
- Migrations are applied automatically on startup (opt-out setting for operators who prefer manual migration).
- **ASP.NET Data Protection keys** are persisted in the DB (via `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore`), so restarts don't invalidate sessions or cookies. They are encrypted at rest with the master encryption key.
- **Redis** is **required for multi-instance deployments** (with PostgreSQL; SQLite is single-instance only). It holds:
  - authorization codes, encrypted under a key derived from each code, and looked up by an ID derived from it, so Redis holds nothing usable without the code
  - rate-limit counters, keyed by an HMAC of the client address or account name
  - change notifications (pub/sub) that wake other instances when settings, signing keys, or the back-channel logout and email queues change; polling stays as the fallback
- Redis holds no copies of database rows (no data cache): clients, users, sessions, and settings always come from the database, so disabling or revoking takes effect at once on every instance.
- When Redis is configured but unavailable, the server fails closed (`503`, readiness unhealthy) instead of falling back to per-instance state.
- A single Redis, Sentinel, and Redis Cluster are supported; a code and its replay marker share a hash slot, so redeeming is atomic in a cluster too. Replication is asynchronous: a primary failover right after a redemption can bring a code back for the rest of its 60 s (documented, accepted).
- Single instance without Redis uses in-process equivalents.
- Jobs that must not run twice at the same moment (signing key rotation) take a lease in the database.

## 4. Protocol support

### 4.1 Grant types

| Grant | Notes |
|---|---|
| `authorization_code` | PKCE (`S256`) **required** for public clients; optional per confidential client (per-client setting), and then only in OpenID Connect requests (`nonce` protects those) |
| `client_credentials` | Server-to-server; confidential clients only |
| `refresh_token` | See token section |

Response type: `code` only. Response modes: `query` (and `form_post` optional).

Authorization responses include the `iss` parameter (RFC 9207) to prevent mix-up attacks; advertised via `authorization_response_iss_parameter_supported` in discovery.

### 4.2 Endpoints

| Endpoint | Spec |
|---|---|
| `/.well-known/openid-configuration` | OIDC Discovery |
| `/.well-known/jwks.json` | JWKS |
| `/connect/authorize` | OAuth 2.0 / OIDC Core |
| `/connect/token` | OAuth 2.0 |
| `/connect/userinfo` | OIDC Core §5.3 |
| `/connect/revocation` | RFC 7009 (refresh tokens) |
| `/connect/introspect` | RFC 7662 |
| `/connect/endsession` | OIDC RP-Initiated Logout |

### 4.3 Client types and authentication

- **Confidential clients:** `client_secret_basic`, and `client_secret_post` only for clients (and API resources) an administrator enabled it for, because RFC 6749 §2.3.1 says it is NOT RECOMMENDED. Secrets stored hashed.
  - Asymmetric client authentication (`private_key_jwt`, OIDC Core §9, RFC 7523; recommended by RFC 9700 §2.5) is planned after v0.1.0 (§14, phase 11a; see Spec deviations).
  - Secrets are generated by the server (256 bits from a CSPRNG) and shown once. Because they are high-entropy, they are hashed with SHA-256 (not a slow password hash) and compared in constant time. The same applies to API resource secrets.
  - Multiple active secrets per client, each with an optional expiry and description, for zero-downtime rotation.
- **Public clients** (SPA / mobile): no secret, PKCE mandatory.
- **Redirect URIs:**
  - Exact string matching; no wildcards or partial matching.
  - Exception for native/CLI apps (RFC 8252): loopback redirects (`http://127.0.0.1` / `http://[::1]`) match on any port.
- **Client ids** can't be GUIDs, so a `client_credentials` token (whose `sub` is the client id) can't be mistaken for a user's (RFC 9700 §4.15). Userinfo and the Admin API also refuse tokens whose `sub` equals their `client_id`.
- Per-client configuration includes:
  - redirect URIs and post-logout redirect URIs
  - allowed grants and allowed scopes
  - back-channel logout URI
  - token lifetime overrides
  - PKCE requirement
  - allowed CORS origins (for SPAs calling the token, userinfo, and revocation endpoints)
  - enabled/disabled flag (disabled clients can't obtain tokens; their refresh tokens are revoked)

### 4.4 OIDC Core mandatory features (§15.1)

- ID tokens signed with RS256.
- `prompt` parameter (`none`, `login`, `select_account`). `prompt=consent` is refused with `consent_required` and not advertised, because there are no consent screens (§3.1.2.1).
- `display` parameter accepted (may be ignored).
- `ui_locales` and `claims_locales` accepted (may be ignored).
- `max_age` and the `auth_time` claim.
- `acr_values` accepted (may be ignored).
- `nonce` validation.
- `at_hash` and `c_hash` claims where they apply.
- Errors returned to `redirect_uri` per spec; never redirect to unregistered URIs.

### 4.5 Scopes and resources

- **Identity scopes:** `openid`, `profile`, `email`, `roles`, `groups`, `offline_access` (enables refresh tokens).
- **API resources:** each has its own audience (`aud`) and set of scopes. Requested API scopes determine the access token's `aud`.
  - An API resource can have its own secret so it can call the introspection endpoint.

### 4.6 Introspection (RFC 7662)

- Callers authenticate as a confidential client or as an API resource with a secret.
- A caller may only introspect tokens issued to it, or whose audience includes it.
- **Refresh tokens:** status comes from the database, so revocation, rotation, and reuse detection are reflected exactly.
- **Access tokens:** validated statelessly (signature, expiry, issuer, audience). Because access tokens are not tracked server-side, introspection cannot report an access token as revoked before it expires.
- Inactive or unknown tokens return `{"active": false}` with no further details.

### 4.7 Logout

- **RP-initiated logout** through `end_session`, with `id_token_hint` and `post_logout_redirect_uri` validation.
  - A signed-in user always confirms the sign-out first, even with a valid `id_token_hint` for the current session (RP-Initiated Logout §2: the OP SHOULD ask).
  - `post_logout_redirect_uri` must exactly match a URI registered for the client identified by the hint or `client_id` (no loopback port exception).
- **Back-channel logout** (OIDC Back-Channel Logout 1.0):
  - ValkyrieID POSTs a signed `logout_token` to each client's registered back-channel URI.
  - ID tokens include a `sid` claim; logout tokens always carry both `sub` and `sid`.
  - Clients are tracked per session when they receive an authorization code.
  - At sign-out, the clients are notified before the post-logout redirect, waiting at most a configurable timeout (default 5 s).
  - Failed deliveries (network errors, timeouts, 408, 429, 5xx) are retried with backoff from a database queue that any instance can process; other responses are final. Each attempt uses a fresh, short-lived logout token, so tokens are never stored.

## 5. Tokens

| Token | Format | Default lifetime |
|---|---|---|
| Access token | Self-contained JWT (RS256, `typ: at+jwt`, RFC 9068) | 30 min |
| ID token | JWT (RS256) | 5 min |
| Refresh token | Opaque, DB-stored (hashed) | 14 days sliding, 30 days absolute |
| Authorization code | Opaque, single-use | 60 s |

A redeemed code is remembered for 10 minutes, so a replay is detected (and the refresh tokens issued from it revoked) after the code itself has expired.

All lifetimes are configurable globally and per client. Token validation allows a small configurable clock skew (default 30 s).

- **Access tokens are not revocable before they expire**; their short lifetime limits the risk.
- **DPoP** (RFC 9449), planned after v0.1.0 (§14, phase 11b; see Spec deviations): clients will be able to bind access tokens to a key (`cnf.jkt`), as RFC 9700 §2.2.1 recommends; refresh tokens of public clients will be bound to the same key, and DPoP can be required per client.
- JWTs are serialized and signed with `Microsoft.IdentityModel.JsonWebTokens` (a JWT library, not a protocol framework). All protocol logic stays in ValkyrieID.
- **Refresh tokens rotate on every use.** Reusing an already-used token revokes the entire token family.
- Refresh tokens are also revoked on revocation endpoint calls, password change, user disable, and client disable, and when an authorization code is replayed.
- **Logout does not revoke refresh tokens.** They are only issued with `offline_access`, which grants access while the user is not signed in (OIDC Core §11); OIDC Back-Channel Logout §2.7 says such tokens normally SHOULD NOT be revoked at logout. Each token still records its session (`sid`).
- `offline_access` is only honored for clients an administrator allowed both the `offline_access` scope and the `refresh_token` grant. With no consent screen, that admin approval is the consent OIDC Core §11 requires; otherwise the scope is ignored.
- **Signing keys:**
  - RSA keys generated automatically and stored encrypted in the DB.
  - Rotated on a configurable schedule.
  - New keys are published in JWKS before they are used for signing; retired keys stay published until the tokens they signed have expired.

## 6. Authentication

- Username and password, hashed with **Argon2id**. Users log in with their **username or email**.
  - Hashing parameters are configurable; the server rejects values below the OWASP Password Storage Cheat Sheet minimums. Default: m=12 MiB, t=3, p=1. Hashes are upgraded to the current parameters at login.
- **Anti user-enumeration:** login, password reset, and registration-related responses are generic ("invalid credentials", "if the account exists, an email was sent"), and password verification runs in constant time even for unknown users.
- **TOTP 2FA** (Google Authenticator compatible):
  - users enroll themselves (QR code)
  - recovery codes
  - TOTP codes accepted within ±1 time step (30 s) to tolerate clock drift; each code can be used only once
  - admins can enforce 2FA globally or per user
  - users with the `admin` role must use 2FA by default (`AdminApi:RequireTwoFactor`): they enroll at their next sign-in, and the Admin API only accepts access tokens whose `amr` shows a second factor (`mfa`; RFC 9470 `insufficient_user_authentication` otherwise). Admin API access tokens carry the sign-in's `amr`; tokens for other audiences don't
- **Configurable password policy:** length, complexity, breached-password check (optional).
- **Account lockout** after N failed attempts, for a configurable duration.
- **Rate limiting** on login, 2FA, and token endpoints.
- **SSO session cookie** (default 8h), shared across clients; respects `prompt` and `max_age`.
- **Email features** (enabled only when SMTP is configured):
  - email verification, optionally prompted for or required after sign-in (`Email:VerificationAtSignIn`: off, prompt, require); required verification stops the authorization request at a verification page (`interaction_required` with `prompt=none`)
  - password reset
- **Session management:**
  - Server-side session records (device/browser, IP, last activity).
  - Users can view and revoke their own sessions.
  - Admins can view and revoke any user's sessions (force logout).
  - Revoking a session (an explicit user or admin action, not a normal logout) triggers back-channel logout and revokes the refresh tokens issued from it.
- **Future:** passkeys / WebAuthn. Their `amr` value must be added to the second-factor list used for 2FA requirements (`AuthenticationMethods.SecondFactor`).

## 7. User model

- Subject identifier (`sub`): an immutable GUID assigned at creation, never the username or email.
- Username, email, email verified, display name, given name, family name.
- Roles and groups.
- Custom key/value claims per user.
- Enabled/disabled flag, lockout state, 2FA state.
- Claims are emitted according to requested scopes.

## 8. User interface

### 8.1 Login pages (server-rendered Razor Pages)

- Login, 2FA, recovery code, 2FA enrollment, password reset, email verification, and logout pages.
- No JavaScript required; strict CSP; anti-forgery tokens.
- **Self-service account page:** change password, update profile (name, email; email change requires re-verification when SMTP is configured), manage 2FA and recovery codes, view and revoke sessions.
  - Sensitive actions (password change, turning 2FA on or off, new recovery codes) require the current password on every submission; there is no "sudo" window. Wrong passwords count towards lockout, and the forms are refused while the account is locked.
  - A password change keeps the current session (its cookie is re-issued with the new security stamp), revokes all other sessions with back-channel logout, and revokes **all** the user's refresh tokens, including the current session's.
  - Turning 2FA off requires the password and a TOTP or recovery code, is refused while 2FA is required, and revokes the other sessions like a password change. The current session keeps its `amr`, which records how it actually authenticated.
  - New recovery codes replace all existing ones and don't affect sessions.
  - Users can only list and revoke their own sessions; revocation uses the shared session service (back-channel logout plus the session's refresh tokens).
- **Branding:** background image, logo, product name/title, colors (CSS variables), optional custom CSS.

### 8.2 Admin UI (Angular, latest version, signals)

- Built as a SPA and served by the same ASP.NET Core app (single container).
- Authenticates through ValkyrieID itself as a public PKCE client (dogfooding).
- Access requires the built-in `admin` role and, by default, a sign-in with a second factor (§6).
- **Manages:**
  - users, roles, groups, and claims
  - clients and API resources/scopes
  - signing keys
  - runtime settings and branding (§10)
- Includes an audit log viewer.
- Talks exclusively to the **Admin REST API**.
- Served under `/admin` with its own CSP (`script-src 'self'`, `connect-src 'self'`, no inline scripts or styles, no framing). Tokens are kept in memory only; with no refresh tokens, it renews them by a top-level `prompt=none` redirect through the SSO session. Uses `oidc-client-ts`, plus the RFC 9207 `iss` check and ID token claim checks it lacks.
- `AdminUI:Enabled=false` turns it off (`/admin` answers 404, its client is disabled), for installations managed with the CLI only.

### 8.3 First-run setup wizard

- Shown when no users exist. Creates the initial admin user, who then sets up 2FA before the session starts (while admins require it, §6). The admin UI client is seeded in phase 8, when the admin UI exists (see §14, roadmap changes).
- Locks itself after completion.

### 8.4 Admin recovery (break-glass)

- **Last-admin guard:** the last enabled user with the `admin` role cannot be deleted, disabled, or have the role removed.
- **CLI reset:** the server binary/container supports maintenance commands (e.g. `valkyrieid admin reset-password <user>`, `reset-2fa <user>`, `unlock <user>`, `grant-admin <user>`) that run against the configured database without starting the web server. Every use is written to the audit log.
  - `admin reencrypt` re-encrypts secrets with the current master key so previous keys can be removed (§10).
- **CLI management:** the same binary also manages users, clients, and API resources (`valkyrieid user …`, `valkyrieid client …`, `valkyrieid resource …`). Before the Admin API (phase 8) this was the only way to create them; both now share the same administration services.
- Passwords are never accepted as CLI arguments; they are read from a hidden prompt or standard input.

### 8.5 Accessibility

- Login pages and admin UI target **WCAG 2.2 AA** (keyboard navigation, labels, contrast, screen reader support).
- Checked automatically with axe (Playwright, `tests/ValkyrieID.A11yTests`) on every page and state, with the default and a custom branding, against a published server on SQLite; a manual pass is recorded in `docs/accessibility/checklist.md`. Operators are responsible for the contrast of custom branding (documented requirements).

## 9. Admin REST API

- JSON API under `/api/admin`, protected by access tokens with the admin scope and role.
- Used by the admin UI; also usable for automation.
- **Authorization** (checked on every request, before routing):
  - the access token is only accepted in the `Authorization: Bearer` header (never the query string or a cookie)
  - it must be a valid access token from this issuer (RFC 9068) whose audience includes the built-in API resource `valkyrieid-admin`, with the scope `valkyrieid.admin`
  - its `sub` must be an existing, enabled, not locked-out user with the `admin` role, looked up in the database on every request, so losing the role or being disabled takes effect immediately even though access tokens can't be revoked
  - tokens without a user (`client_credentials`) are never accepted; automation signs in as an admin user or uses the CLI
  - while `AdminApi:RequireTwoFactor` is on (default), the token's `amr` must show a second factor (§6)
- **Built-in entities:** the server seeds the `valkyrieid-admin` resource and the `valkyrieid-admin-ui` public PKCE client (authorization code only, no refresh tokens, 10-minute access tokens, redirect URIs derived from the issuer). They are read-only, and their names are reserved.
- No CORS (the admin UI is same-origin). Responses are `no-store`. Errors are RFC 9457 problem details; lists use `limit`/`offset`, the audit log a keyset cursor. Concurrent edits: last write wins.
- Every change is audited with the actor `admin:<sub>`. Clients, resources, and users are managed through the same services as the CLI.
- `AdminApi:Enabled=false` turns it off: `/api/admin` answers 404, the admin resource is disabled so no admin tokens can be issued, and the admin UI is off too.

## 10. Configuration

- **Base config:** `appsettings.json` and environment variables (DB provider, connection string, Redis, issuer URL, master encryption key).
- **Master encryption key:**
  - Supplied through env/config; required at startup.
  - Encrypts secrets at rest (AES-256-GCM): signing keys, TOTP secrets, SMTP password, Data Protection keys.
  - Supports key rotation (re-encrypt with a new key while the old one is still configured, using `valkyrieid admin reencrypt`).
- **Runtime settings** (token and session lifetimes, email link lifetimes, branding, SMTP, password policy, lockout, 2FA enforcement, admin 2FA requirement, email verification at sign-in, audit log retention):
  - editable in the admin UI, the Admin API, and the CLI (`settings show|set|reset`), and stored in the DB (one row per setting; an allow-list decides which keys can be stored)
  - **values from appsettings/env take precedence** and are shown as locked in the admin UI. The DB is the lowest-precedence configuration source, so options binding and validation are unchanged
  - changes are validated together with the configuration before saving, audited (secrets as `(secret)`), and picked up without a restart: the writing instance at once, other instances and processes when notified through Redis, and otherwise by polling a settings revision (`Settings:ReloadInterval`); invalid stored values are not applied on reload, and stop startup like any invalid configuration
  - the SMTP password is encrypted with the master key, never returned by the API, and covered by `admin reencrypt`
  - configuration-only: infrastructure (DB, Redis, issuer, master key, proxy), signing keys, password hashing, rate limits, clock skew, the branding directory, and the breached-password API URL (an admin-set URL would allow SSRF)

## 11. Operations

- **Audit log** in the DB: logins, failures, lockouts, token issuance, admin changes. Viewable in the admin UI, with configurable retention (default 365 days; 0 keeps entries forever).
- **Health endpoints:** liveness and readiness (DB and Redis checks).
- **OpenTelemetry** traces, metrics, and logs over OTLP; enabled when `OTEL_EXPORTER_OTLP_ENDPOINT` is set.
- Structured logging.
- **Reverse proxy support:**
  - Forwarded headers (`X-Forwarded-For`, `-Proto`, `-Host`) with configurable trusted proxies.
  - Public issuer URL configured explicitly (never derived from the request).
  - Optional path base (e.g. `/auth`).
- **Transport security:** while the issuer is `https`, requests that didn't arrive over HTTPS are refused (`400`, no redirect), except the health endpoints (RFC 6749 §3.1, §3.2). Behind a TLS-terminating proxy, the proxy must be trusted. HSTS with a one-year `max-age` by default (`Hsts:*`, configuration-only).
- **Security headers:**
  - HSTS, Content-Security-Policy, `X-Frame-Options: DENY` / `frame-ancestors 'none'`, `X-Content-Type-Options`, `Referrer-Policy`.
  - CSP `form-action 'self'`; sign-in and sign-out pages add the origin of a validated redirect URI, because browsers apply `form-action` to the redirects after a form post.
  - Pages and protocol responses are `no-store`; redirects answering a `POST` are `303` (RFC 9700 §4.12).
  - The admin UI and the Admin API add `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` (not the login and protocol pages, where COOP would break popup sign-in).
  - Cookies are `Secure`, `HttpOnly`, and `__Host-` prefixed, with an appropriate `SameSite` setting.
  - The checklist of RFC 9700 §4 and OIDC Core §16 mitigations is kept in `docs/security/checklist.md`.
- **CI: GitHub Actions**, kept within the free tier (public repo: free standard runners; private: 2,000 min/month):
  - **On every push / PR** (fast, Linux runners only):
    - locked-mode restore
    - build with warnings as errors
    - `dotnet format --verify-no-changes`, `prettier --check`, lint
    - unit tests and SQLite integration tests
    - Angular tests, `prettier --check`, and lint; a `dotnet publish` that includes the admin UI
  - **On PRs to `main`:** add PostgreSQL and Redis integration tests (Testcontainers), and the accessibility checks (Playwright and axe against the published server, Chromium only).
  - **On release tags / manual trigger only:** Docker image build (amd64 and arm64) and footprint check, image publish, OpenID conformance suite, OWASP ZAP scan.
  - **Nightly:** OpenID conformance suite (all plans), to catch regressions between releases.
  - **Cost controls:**
    - Linux runners only (Windows/macOS minutes cost 2×/10× on private repos).
    - NuGet and npm caching.
    - Path filters (e.g. docs-only changes skip builds).
    - `concurrency` with `cancel-in-progress` so superseded runs stop.
    - Job timeouts.
- **Versioning & releases:**
  - Semantic versioning; Git tags trigger release builds.
  - Docker images published to GitHub Container Registry as `ghcr.io/valkyrieid/valkyrieid`, tagged with the version and `latest`.
  - Release notes per version.
  - Images for amd64 and arm64. The first release is `v0.1.0`.
- **Documentation** (in this repository, under `/docs`):
  - Built with **VitePress** (Markdown, built-in local search).
  - Hosted on GitHub Pages at **https://valkyrieid.liesel.dev**, deployed by a GitHub Actions workflow on push to `main` when files under `/docs` change.
  - Contents:
    - Getting started (Docker and `dotnet publish`).
    - Configuration reference (all settings and env vars).
    - Integration guides (ASP.NET Core, Angular/SPA, server-to-server).
    - Operations guide (reverse proxy, multi-instance with Redis, backups, key rotation, upgrades).
  - The server repo's README stays short (what it is, quick start) and links to the docs site.
  - Changes to configuration or behavior include the matching docs update in the same PR.
- **Deployment:**
  - small chiseled Docker image (`aspnet:10.0-noble-chiseled-extra`, framework-dependent, amd64 and arm64), running as non-root, with a health check through `valkyrieid healthcheck` (the image has no shell or curl)
  - plain `dotnet publish` output
- **Footprint targets** (measured in CI on release builds and manual runs, `footprint/measure.*`):
  - Docker image < 210 MB
  - Idle memory < 150 MB
  - Startup to ready < 4 s (SQLite, fresh volume, timed from `docker start`)
  - Revised in phase 10b (2026-11-07) from < 120 MB and < 2 s: the chiseled ASP.NET Core base alone is 124 MB, and 163 MB with ICU and time zone data (`-extra`), kept for culture-aware formatting and time zones. ReadyToRun met the 2 s startup target but added about 30 MB; the image stays JIT-only (180 MB, 2.5–3.0 s, ~100 MB idle when measured).
- **Backups:** documented backup and restore procedures for SQLite (online backup / file copy while stopped) and PostgreSQL (`pg_dump`). Backups must be paired with the master encryption key, since secrets in the DB are unreadable without it.

## 12. Development conventions

- **Central Package Management:** all NuGet versions live in `Directory.Packages.props` (`ManagePackageVersionsCentrally=true`). Project files reference packages without versions.
- **Adding dependencies:**
  - Always add packages through the CLI, never by hand-editing project files:
    - `dotnet add package <name>` (with Central Package Management this writes the version to `Directory.Packages.props`)
    - `npm install <name>` / `ng add <name>`
  - Always use the latest stable version at the time of adding.
  - Check for outdated packages regularly: `dotnet list package --outdated` and `npm outdated`. Also check for vulnerable packages: `dotnet list package --vulnerable` and `npm audit`.
- **NuGet lock files:** `RestorePackagesWithLockFile=true`; `packages.lock.json` is committed. CI restores with `--locked-mode` (`RestoreLockedMode=true` when `CI=true`).
- **Shared build settings** in `Directory.Build.props`:
  - `TreatWarningsAsErrors=true`
  - `LangVersion=latest` (C# 14 on .NET 10); use the latest syntax, e.g.:
    - file-scoped namespaces
    - primary constructors
    - collection expressions
    - `field` keyword
    - extension members
    - pattern matching
  - `Nullable=enable`
  - `ImplicitUsings=enable`
  - `AnalysisLevel=latest`
  - `EnforceCodeStyleInBuild=true`
- **`.editorconfig`** defines code style; style violations fail the build.
- **Formatting:**
  - .NET: `dotnet format`. CI runs `dotnet format --verify-no-changes` and fails on unformatted code.
  - Angular: **Prettier**. CI runs `prettier --check` and fails on unformatted code. ESLint is configured with `eslint-config-prettier` so it doesn't conflict with Prettier's formatting.
- **Solution format:** `.slnx`.
- **Angular:**
  - `package-lock.json` committed; CI uses `npm ci`.
  - TypeScript `strict` mode; lint errors fail the build.
  - **Signals for all component state**: `signal`, `computed`, `input()`, `output()`, `model()`, and `resource`/`httpResource` for data loading.
  - **`ChangeDetectionStrategy.OnPush` on every component**, enforced by lint rule.
  - Standalone components, built-in control flow (`@if`, `@for`), and `inject()` instead of constructor injection.
  - **Zoneless** change detection (no zone.js).
- **Dependabot** opens weekly PRs for NuGet, npm, GitHub Actions, and Docker base image updates (minor/patch updates grouped).

## 13. Testing

- xUnit unit tests and integration tests (`WebApplicationFactory`, against both SQLite and PostgreSQL).
- Angular unit tests.
- **Accessibility checks** (`tests/ValkyrieID.A11yTests`, Playwright with `@axe-core/playwright`): every login page and admin UI route and state, with the default and a custom branding; fails on WCAG 2.2 A/AA violations, reflow at 320 CSS px, motion with reduced motion, hidden focus, and CSP violations.
- **OpenID Foundation Conformance Suite**, self-hosted in Docker for CI and local runs; optionally the hosted suite, run manually against a publicly reachable deployment. Target plans:
  - Basic OP
  - Config OP
  - RP-Initiated Logout
  - Back-Channel Logout

  A release requires every plan to pass with no failures; each warning is either fixed or documented with its reason. Results are published in the docs as "passes the OpenID conformance suite", never as "OpenID Certified" (see §2).
- **OAuch** (oauch.io): OAuth 2.0 security best-practice testing (RFC 9700). Covers PKCE downgrade, redirect URI manipulation, code replay, and refresh token rotation.
- **Client compatibility tests** against real client libraries and apps:
  - ASP.NET Core `AddOpenIdConnect` / `AddJwtBearer`
  - oidc-client-ts / angular-auth-oidc-client (via the admin UI)
  - oauth2-proxy
  - Grafana generic OAuth
- **Security scanning** with OWASP ZAP: baseline and API scans, a full active scan of the login pages, and an authenticated scan of the Admin API.

11. **Protocol additions** *(deferred: from phase 10; after v0.1.0)*:
    - **11a: `private_key_jwt` client authentication** (OIDC Core §9, RFC 7523; RFC 9700 §2.5). Design decided while planning (2026-11-05):
      - keys: a public JWKS stored on the client or API resource; no `jwks_uri` (no outbound fetches, so no SSRF or key caching). Validated on save: public keys only, RSA ≥ 2048 bits or EC P-256/384/521, `use` = `sig` or absent, unique `kid`s, size limits. Rotation by publishing old and new keys together
      - one authentication method per client or resource (`client_secret` or `private_key_jwt`); `private_key_jwt` entries have no secrets, so they can't fall back to one. EF Core migrations for both providers
      - API resources can use it at the introspection endpoint (`iss`/`sub` = resource name)
      - at the token, introspection, and revocation endpoints; mixed methods in one request (RFC 6749 §2.3) are rejected; `client_assertion_type` must be `urn:ietf:params:oauth:client-assertion-type:jwt-bearer` (RFC 7521 §4.2)
      - `aud` must be the issuer as its sole value (draft-ietf-oauth-rfc7523bis §4, the audience-injection fix), not the token endpoint URL that OIDC Core §9 suggests to clients; stricter than OIDC Core, no deviation
      - `iss` = `sub` = client_id; `exp` and `jti` required; `nbf`/`iat` checked with the clock skew; maximum assertion lifetime (default 5 min, configuration-only)
      - algorithm allow-list RS/PS/ES 256–512; no `none`, no HMAC; `alg` must match the key type; `kid` selects the key (without `kid` only when a single compatible key exists); `jku`, `x5u`, `jwk`, `x5c`, and `crit` headers rejected
      - `typ`: absent, `JWT`, or `client-authentication+jwt`; other explicit types rejected
      - `jti` replay protection until `exp` + skew, in Redis when configured (atomic, shared by all instances) or in process otherwise; fails closed when Redis is unavailable
      - failures answer `invalid_client` and are audited with a specific reason; the assertion is never logged
      - advertised in discovery (`*_endpoint_auth_methods_supported`, `*_endpoint_auth_signing_alg_values_supported`)
      - CLI, Admin API, and admin UI support
      - conformance setup: a `private_key_jwt` variant of the Basic OP plan (first check which `aud` the suite sends)
    - **11b: DPoP** (RFC 9449; RFC 9700 §2.2.1)
      - proof validation (`htm`, `htu`, `iat`, `jti` replay, optional server nonce), `cnf.jkt` in access tokens
      - refresh tokens of public clients bound to the DPoP key
      - per-client DPoP requirement; advertised in discovery

### Spec deviations

Every approved deviation from a SHOULD / RECOMMENDED requirement is listed here. MUST-level requirements are never deviated from.

| Spec section | Level | Deviation | Reason | Date |
|---|---|---|---|---|
| RFC 7009 §2 | SHOULD | Access tokens can't be revoked; the revocation endpoint answers `unsupported_token_type` for them. | Access tokens are self-contained JWTs (RFC 9068) that resource servers validate without calling ValkyrieID. Their short lifetime (30 min default) limits the risk (§5). | 2026-10-29 |
| RFC 7009 §2.1 | SHOULD | Revoking a refresh token doesn't invalidate access tokens issued from the same grant. | Same reason: access tokens aren't tracked server-side. They expire within their lifetime. | 2026-10-29 |
| RFC 9700 §2.1.1 | RECOMMENDED | An administrator can turn PKCE off for a confidential client (`--no-pkce`), for OpenID Connect requests only. On by default; always required for public clients and for requests without `openid`. | Some confidential clients (and the conformance plans) don't send PKCE. OIDC `nonce` is the spec's alternative protection against code injection for those clients. | 2026-10-29 |
| OIDC Discovery §3 | RECOMMENDED | No `registration_endpoint`. | Dynamic client registration is a non-goal (§2). | 2026-10-29 |
| RFC 9700 §2.5 | RECOMMENDED | No asymmetric client authentication (`private_key_jwt`, mTLS) in v0.1.0. | Client secrets are 256-bit, server-generated, stored hashed, compared in constant time, can expire, and rotate without downtime. The target clients mostly use secrets. Planned after v0.1.0 (§14, 11a). | 2026-11-05 |
| RFC 9700 §2.2.1 | SHOULD | Access tokens aren't sender-constrained (no DPoP or mTLS) in v0.1.0. | Access tokens are short-lived; refresh tokens rotate with reuse detection, which meets the §2.2.2 MUST for public clients. Common resource servers (ASP.NET Core JwtBearer, oauth2-proxy, Grafana) can't check DPoP proofs. Planned after v0.1.0 (§14, 11b). | 2026-11-05 |
| RFC 9700 §4.16 | SHOULD | Administrators can't configure allowed framing origins per client; every response sends `frame-ancestors 'none'` and `X-Frame-Options: DENY`. | Stricter than the spec: nothing can frame the login pages. Silent renew in iframes is broken by third-party cookie blocking anyway; clients use top-level `prompt=none` redirects (as the admin UI does) or refresh tokens. | 2026-11-05 |
